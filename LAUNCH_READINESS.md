# IRBI: готовність до першого замовлення

Стан перевірки: 19.11.2026. Це перелік фактичних перевірок і відкритих умов запуску, не сертифікат готовності.

## Перевірено

- Серверний цикл у транзакції з ROLLBACK: клієнт створює заявку; координатор погоджує час, ціну й тривалість; призначає клінера; клінер проходить accept/depart/arrive/start; незаповнений чек-лист блокує завершення; заповнений дозволяє finish; адміністратор реєструє оплату, погоджує та фіксує виплату клінеру.
- Звірка тестового замовлення: оплата 1200, праця 600, маржинальний результат 600 без інших витрат.
- Повторна заявка з тим самим ідентифікатором повертає той самий номер. Зміна вже прийнятого запиту відхиляється.
- Повторна оплата з тим самим ідентифікатором не дублюється. Сума понад залишок відхиляється. Клієнт не може реєструвати оплату.
- Тестові записи та тимчасові зміни ролей відкочено. Постійних тестових адміністратора/клінера не створювали.
- Непотрібні TRUNCATE/REFERENCES/TRIGGER відкликані в anon/authenticated у схемі public; перевірка залишкових дозволів повернула 0.
- У репозиторії є автоматичні регресійні тести, перевірка локальних HTML-посилань та імпортів модулів. CI налаштований для pull request і main; його віддалений запуск ще треба перевірити.

## Серверні зміни вже застосовано

- customer_request_once: захист від повторних клієнтських запитів;
- manual_payments: адміністративний облік фактично отриманих коштів;
- revoke_client_ddl_privileges: видалення непотрібних прав адміністрування таблиць.

Поточний опублікований frontend не містить змін із PR №1. Факт наявності коду в PR не означає, що функція вже доступна клієнтам.

## Умови, що залишаються до запуску

1. Визначити й авторизувати постійний акаунт власника-адміністратора. Зараз профілі: 3 customer, 1 dispatcher, жодного admin/cleaner. Не підвищувати ролі автоматично.
2. Додати реального клінера через адміністратора; перевірити кожну роль у браузері, у тому числі відмови доступу до чужих замовлень, фінансів, фотографій та нарахувань.
3. Перевірити PR, CI, злиття й публікацію. Після публікації повторити реєстрацію/підтвердження email/відновлення пароля і контрольний шлях у браузері на телефонному екрані.
4. Визначити робочий канал оповіщення координатора. Внутрішній inbox клієнта не замінює оперативне повідомлення команді про нову заявку.
5. Опублікувати погоджені власником склад послуг, правила переносу/скасування, порядок претензій, відомості виконавця й інформацію про обробку даних. Не вигадувати реквізити, строки, штрафи та обіцянки.
6. Перевірити фактичну доставку prelaunch-лідів у робочу систему, резервне копіювання й порядок відновлення.
7. Доробити контрольоване перенесення/скасування підтвердженої роботи та відмову клінера. До цього координатор має мати перевірений ручний порядок обробки таких випадків.
8. Доробити стійкість записів складу, фото й інших окремих дій при обриві зв'язку. Не повторювати сумнівні записи без звірки.
9. Підписки, онлайн-еквайринг, автоматичні повернення та push не вважати готовими: поточний сценарій — запит із ручним підтвердженням і ручною реєстрацією отриманої оплати після завершення.

## Команди перевірки

```sh
node --test tests/*.cjs tests/*.mjs
for source in *.js; do node --check "$source" || exit 1; done
git diff --check
```

SQL-перевірки з суфіксом `_rollback.sql` запускати цілком, включно з BEGIN і ROLLBACK. Сквозний тест використовує поточні профілі лише всередині незакоміченої транзакції та потребує трьох customer і одного dispatcher.
