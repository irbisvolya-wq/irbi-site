# IRBI: готовність до першого замовлення

Оновлено: 25.11.2026. Детальна перевірка архітектури: [аудит](docs/ARCHITECTURE_AUDIT_2026-11-25.md).

## Перевірено

- Frontend злитий у main; публікація працює через GitHub Pages, а не Vercel. Сайт залишається у режимі підготовки до запуску.
- Серверний цикл з ізольованими фікстурами: заявка, погодження часу/ціни/тривалості, призначення, робочі статуси, чек-лист, завершення, ручна реєстрація отриманої оплати, погодження й облік виплати.
- Фінансова звірка тестового замовлення: отримано 1200, праця 600, залишок після цих затрат 600.
- Клієнт не читає й не скасовує чужу заявку, не змінює ціну прямим записом і не підвищує собі роль.
- Повторні клієнтські заявки та ручні оплати мають серверні ідентифікатори спроб.
- Усі 17 викликаних frontend RPC існують; користувацькі таблиці public мають RLS. Фінансові представлення використовують security_invoker.
- Адміністратор існує. Профілю реального клінера на момент перевірки немає.
- 46 результатів Node test runner успішні; синтаксис JS, локальні посилання й імпорти перевірено.
- SQL-перевірка виконана до і після застосування архітектурної міграції; тестові записи відкотилися. Вона не є частиною GitHub CI.

## Серверні зміни вже застосовано

- customer_request_once: захист від повторних клієнтських заявок;
- manual_payments: облік отриманих коштів;
- revoke_client_ddl_privileges: відкликання зайвих дозволів;
- architecture_integrity_20261125: збереження додаткових робіт клієнта під час налаштування об'єкта, єдиний запис історії переходу зі збереженням коментаря, явна відмова доступу до фото для користувача без профілю.

Файл міграції: supabase/patches/2026-11-25_architecture_integrity.sql. Не застосовувати повторно без перевірки історії міграцій.

## Умови запуску, які залишаються

1. Визначити реального клінера й акаунт; перевірити його робочий шлях на телефоні та доступ кожної ролі в браузері.
2. Перевірити фактичну доставку підтверджень email і відновлення пароля.
3. Підключити й перевірити робочий канал сповіщення координатора; внутрішній inbox клієнта його не замінює.
4. Забезпечити обробку prelaunch-лідів; end-to-end синхронізація з HubSpot не підтверджена.
5. Погодити й опублікувати реквізити виконавця, контакти, склад послуг, правила переносу/скасування, претензій і обробки даних. Не вигадувати умови.
6. Перевірити резервне копіювання, відновлення бази й файлів Storage. Вихідні коди Edge Functions збережені; повної відтворюваної схеми ще немає.
7. Доробити керований перенос, скасування підтвердженої роботи й відмову клінера або затвердити перевірений ручний порядок.
8. Доробити відновлення окремих записів фото, складу та витрат після невизначеного результату й перезавантаження.

Поточний робочий сценарій: попередній запит, ручне погодження і ручний облік фактичної оплати. Підписки, автоматична генерація візитів, еквайринг, повернення й push не називати готовими.

## Команди перевірки

```sh
node --test tests/*.cjs tests/*.mjs
for source in *.js; do node --check "$source" || exit 1; done
```

Новий самодостатній SQL-тест: supabase/tests/architecture_integrity_rollback.sql. Запускати весь файл, включно з BEGIN і ROLLBACK. Старі SQL-тести можуть залежати від колишнього складу профілів; не змінювати ролі реальних користувачів для їх запуску.
